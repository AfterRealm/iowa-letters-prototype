About this build

A short note from the applicant. This prototype site, both the content and the build, is my cover letter for the Web Application Developer (Digital Scholarship & Publishing Support) position at Libraries Information Technology.

Why I built this instead of a cover letter

A cover letter PDF can describe a way of working. A working prototype shows one. I wanted you to be able to read the posting's specific responsibilities ("implementing and supporting CMS… commonly used in library and digital publishing contexts, such as Omeka," "modernizing existing applications," "contributing to system analysis and technical design activities based on requirements defined by the Research Manager," "applying established development standards") and then open this site and see those exact responsibilities embodied in a small but real artifact.

I am not currently a Libraries developer. This prototype is my attempt to demonstrate, in the most direct way I know how, what working with me on a DSPS project might look like in its first delivered milestone.

How I would have approached this if it were a real DSPS project

Reading the posting carefully, the developer in this role works in partnership with the Research Manager in DSPS Studio, who serves as Product Owner and Business Analyst. The developer's first job in this role is not code. It is discovery, requirements clarity, and maintainability. Here is the rough shape of how I would have worked this project:

Step 1 · Discovery

Questions I would have asked the Research Manager and the faculty PI before writing a line of code

  • Who is the primary audience: scholarly, undergraduate-teaching, public, or all three?
  • What is the lifespan of this edition? Is it tied to a grant cycle, or expected to live for ten or twenty years?
  • Where will the primary source images come from, and what is the digitization pipeline that produces IIIF manifests for them?
  • Who maintains this in three years, in five years, after the PI retires?
  • Are there accessibility requirements beyond WCAG 2.2 AA, for example requirements specific to a funding body?
  • Does the project need to expose its metadata for harvest by aggregators (DPLA, OAI-PMH endpoint)?
  • Are there comparable editions already published by Iowa Libraries that this should look and feel consistent with?
Step 2 · System design

The system shape I would have proposed for review by the Application Development lead

Backend
An Omeka S instance hosting items, item sets, resource templates. Curatorial work happens in Omeka's admin UI by Special Collections staff with role-scoped access. Faculty PI gets a curator role to review and approve before publication.
Front-end
An Astro 5 site (matching the pattern LIT is currently using on newer digital edition projects) consuming the Omeka S JSON-LD API. Static-site-generated at build time for performance, accessibility, and long-term sustainability.
Image delivery
IIIF Presentation API 3.0 manifests served from the existing digitization pipeline. Front-end uses Mirador or Clover Viewer.
Search
Client-side fuzzy search for small editions (under a few thousand items). Server-side indexed search (via Omeka S's native search, or an external index) for larger editions.
Deploy
Astro front-end on Cloudflare Pages or a Libraries-managed static host, deployed via GitHub Actions on push. Omeka S backend on whatever infrastructure LIT prefers (Reclaim Hosting, internal VM, etc.).
Step 3 · Standards adherence

What I would have checked against before requesting review

  • WCAG 2.2 AA accessibility audit (axe DevTools + manual keyboard + screen reader smoke test)
  • Dublin Core Terms used correctly; local properties documented in a project vocabulary file in the repo
  • IIIF manifests validated against the IIIF 3.0 spec
  • README and methodology page describing standards used, decisions made, and trade-offs taken, in plain language for the faculty PI and a future maintainer
  • Git history clean, semantic commit messages, no secrets committed
Step 4 · The Omeka S backend, actually built

What I stood up alongside this prototype, so the claim isn't notional

Rather than describe the Omeka S backend in the abstract, I built it. The same six letters in the same Resource Template are running in a real Omeka S 4.1.1 instance, modeled in Dublin Core, organized in an Item Set, published through a Site, and exposed via the REST API I used to populate them programmatically.

  • Custom Dockerfile on PHP 8.3 FPM with all required extensions, built because every public Omeka S Docker image was stale or misconfigured
  • Three-service Compose stack: MariaDB, PHP-FPM, nginx
  • One Resource Template ("Civil War Letter") with twelve Dublin Core properties
  • One Item Set ("Iowa Letters, 1862-1865") grouping the collection
  • Six Items, each modeled in full Dublin Core
  • One Site with a custom homepage and the item set attached
  • All authored programmatically against Omeka's REST API. That is the same automation surface a faculty publishing pipeline would use.

It is live at https://iowa.dev.01.ngrok.dev/s/iowa-letters for as long as my development machine is up. Screenshots of the admin and public side are embedded on the methodology page.

Step 5 · Honest unknowns

Where I would lean on mentorship from the Application Development lead

The job description explicitly says this role receives guidance and mentorship from the Application Development lead. I read that as an invitation to be honest about what I would want help with, rather than to pretend I have every answer.

Drupal 7 to Islandora Modern migrations
I understand the general shape of the migration (Drupal 7 to Drupal 10/11 underneath, content audit, Migrate API, parallel staging, read-only cutover), but I have not personally run an Islandora migration. I would expect to shadow one before I led one.
Omeka S module development at depth
I have read the Omeka S module architecture and the Laminas patterns it sits on. I am comfortable building a small module against documentation; I would want code review on my first real module before it shipped to a production site.
Institutional infrastructure conventions
Things like the preferred hosting model for Omeka instances at Iowa, how user provisioning works for faculty PIs, what the SSO story looks like for curatorial accounts, and what the established Git workflow conventions are inside LIT. These are the kind of things I would want to learn early from the lead and from the existing repos.
Step 6 · Sustainability and handoff

How I would have thought about the next developer who touches this site

  • A README that explains why the choices were made, not just what the choices were
  • The methodology page kept in the same repo as the code, version-controlled together
  • A migration note in the README explaining how to swap the JSON data file for a live Omeka S API call (here, that swap is a one-line change in site.js)
  • Comments at non-obvious decision points, not anywhere else
  • An open issue list for known limitations

What this prototype is not

It is not a finished publication. The transcriptions are fabricated. There is no editorial workflow, no faculty review cycle, no real corpus, no actual digitization pipeline yet. The point is the shape of the work, not the scholarly content. The Omeka S backend is real and runs the same six items, but it too uses the illustrative metadata above; a production version would replace those with actual Special Collections holdings reviewed by curators.
