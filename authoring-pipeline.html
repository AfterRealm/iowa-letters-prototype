Authoring Pipeline

Build notes for the live authoring loop: how the public form on this site writes a new letter to a real Omeka S backend, how the map picks up that letter on its next short-poll, the role-bounded user model that keeps the public form's blast radius small, and what would change between this prototype and a production deployment behind institutional SSO.

Why this exists in the prototype

The GIS Developer/Specialist posting names "supporting digital mapping projects from inception through completion, including workflow optimization and legacy project migration" as a core responsibility of the role. That language is the reason this authoring form exists. A Research Manager in the Studio partnering with a faculty PI on a map-driven project should not have to learn the Omeka admin in order to add a single record. They should be able to fill in a form. This is the smallest, most concrete version of that form, wired all the way through.

The role-bounded user model

The Function POSTs to Omeka as a separate user, iowa-letters-author, created with Omeka S's Author role. The Author role is the smallest role in Omeka that can create new items; it cannot edit other users' records, cannot delete anything, cannot reach the global admin dashboard, cannot modify resource templates, vocabularies, or sites. Even in the unlikely event of a server-side credential leak, the worst-case blast radius is unwanted new-item POSTs — and those can be deleted from the admin and the key rotated by re-running omeka-lab/setup-author-user.mjs.

This is the right shape for a digital scholarship prototype that puts an authoring form in front of strangers. The admin's REST key never leaves a developer workstation. The role-bounded key lives only as Netlify environment variables on the server.

The passphrase gate

The form is gated behind a passphrase that is enforced on both sides of the network boundary. The browser-side check is purely a UX nicety; the real auth boundary lives in the Function:

  • Browser-side: the user enters a passphrase to reveal the form. Nothing about that string is validated locally — it is simply stashed and sent with every submission. A savvy visitor who bypasses the client gate still cannot POST without the correct passphrase.
  • Server-side: every submission goes to /.netlify/functions/post-letter, which compares the supplied passphrase against the IOWA_LETTERS_PASSPHRASE environment variable. If the comparison fails, the function returns 401, the browser re-shows the gate screen, and Omeka is never touched.
  • Credentials: OMEKA_AUTHOR_KEY_ID and OMEKA_AUTHOR_KEY_CRED live only as Netlify environment variables, read by the function and forwarded to Omeka on the server side. The browser-shipped JavaScript bundle contains zero secrets.
  • In a production deployment at University of Iowa Libraries, this two-layer gate would be replaced with institutional Single Sign-On. The form would render only for authenticated users with the appropriate role (Studio staff, faculty PIs, project collaborators), and the Function would be replaced with an authenticated route under the libraries.uiowa.edu hostname.

The honest framing of the prototype's security model: a shared passphrase is enforced server-side, the Omeka credential never leaves Netlify's environment-variable store, and the Author role caps blast radius to creating new items even if both layers were somehow defeated.

CORS and the cross-origin path

The static front-end is served from Netlify; the Omeka backend is exposed through ngrok. Those are different origins, which means the browser refuses cross-origin POST requests unless the server explicitly returns CORS headers. The Omeka container's nginx config (in the iowa-omeka-lab repo) was updated to:

  • Match origins from localhost for local development, *.netlify.app for previews and production, and *.ngrok.dev / *.ngrok-free.app for tunneled access.
  • Return preflight responses (OPTIONS 204) with the appropriate Access-Control-Allow-* headers.
  • Mirror those headers on the actual /api/ response, both at the /api/ location block and the downstream \.php$ location (nginx clears add_header on re-routing between locations, so the headers have to be declared twice).

In production, the Omeka and the front-end would be on the same hostname (under libraries.uiowa.edu or similar) and CORS would be unnecessary. The prototype's CORS configuration documents the workaround pattern for the deployed-elsewhere case.

Live update from form to map

The two pages are decoupled. The form doesn't notify the map directly; instead, the map page polls Omeka on a 12-second cadence and diffs the returned items against the set of letter ids it already knows about. New ids trigger a flyTo, a brief yellow pulse animation around the new pin, and an auto-opened popup. Polling is honest about its limits: it shows a "Live updates paused" banner after three consecutive Omeka failures.

The query-string parameter ?focus=<id> on the map URL tells the page to wait for that specific item to land (up to thirty seconds) and select it automatically. The form's success block links to /map.html?focus=<id>, so a visitor who submits a letter and clicks "Open the map to see it" lands on a map that's already focused on their contribution.

What would change in production

  • Authentication. Replace the passphrase gate with University of Iowa institutional SSO. The Omeka API key becomes a server-side session credential, not a browser-shipped string.
  • Authorization. Per-project authoring permissions through Omeka's site-scoped user roles, so a faculty PI's collaborators can author against their project's templates without inheriting access to other Studio projects.
  • Review queue. New items POST to a draft queue rather than directly to the public site. A Studio staff member reviews and approves before the new record becomes public on the map. This is the workflow most digital scholarship projects actually want.
  • Live update. Replace the 12-second poll with Server-Sent Events from a Node middleware that subscribes to Omeka's resource_updated hook. The graceful-degradation banner pattern stays as a fallback.
  • Audit trail. Every form submission carries a record of who submitted it, from what IP, with what authenticated identity. Omeka has the columns; institutional SSO provides the identity.
  • Validation. Server-side schema validation on the Omeka side, including required-field enforcement, vocabulary validation against the gazetteer, and reject-on-out-of-range date or geometry. Most of this is one Omeka module away.

Repo layout for the authoring side

iowa-demo/
  add-letter.html              ← gated form + success block
  netlify/
    functions/
      post-letter.js           ← server-side proxy: passphrase check +
                                 Omeka credentials, all from env vars
  assets/
    js/
      add-letter.js            ← gate, validate, build payload, POST
      author-key.js            ← public config only (API_BASE, PROPS, etc.)
                                 NO credentials, generated at deploy time
  data/
    gazetteer.json             ← shared with the map's autocomplete

iowa-omeka-lab/
  nginx.conf                   ← CORS rules for /api/ and the .php handler
  setup-author-user.mjs        ← creates iowa-letters-author + generates key
  author-credentials.env       ← gitignored, output of setup-author-user.mjs

The author-key.js file is regenerated on every Netlify deploy by scripts/build-author-key.js and holds only the public configuration (API base URL, Resource Template id, Dublin Core property ids). The actual secrets live in three Netlify environment variables: IOWA_LETTERS_PASSPHRASE, OMEKA_AUTHOR_KEY_ID, and OMEKA_AUTHOR_KEY_CRED. The Function is the only code that reads them; the browser never sees them.
