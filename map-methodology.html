Map Methodology

Build notes for the map view: how letters get from dcterms:spatial strings in Omeka to pins on a MapLibre map, why a controlled-vocabulary gazetteer sits between them, and which library and data-format choices reflect the named requirements of the LIT GIS Developer role.

The data pipeline

The map is the consumer end of a small pipeline that takes the digital edition's source records and produces three interchange-format outputs in parallel.

data/items.json        ── source records (Dublin Core)
data/gazetteer.json    ── curated place authority (canonical name → WGS 84)
       │
       ▼  scripts/build-spatial.py  (pure Python + pyshp)
       │
       ├── data/letters.geojson    RFC 7946 FeatureCollection
       ├── data/letters.csv        flat tabular with WKT geometry column
       └── data/letters.shp + .shx + .dbf + .prj   ESRI Shapefile

The pipeline is a single small Python script (scripts/build-spatial.py) chosen over geopandas or fiona because the dataset is small and the dependency footprint should match what's likely already installed on a Libraries IT workstation. The same shape of work in a production geoprocessing context would be done with ArcPy (against an ArcGIS Pro project) or PyQGIS (against a QGIS project) — both are drop-in replacements for the few transformations this script does. The current implementation depends only on pyshp for Shapefile serialization, so the pipeline reproduces on any machine with Python 3.9+ and pip.

Why all three formats

The GIS Developer/Specialist posting names GeoJSON, SHP, CSV, and XML as the geospatial data formats Libraries IT staff are expected to be comfortable with. Emitting all three readable formats from a single source of truth is the right pattern for a digital scholarship project: different audiences need different formats.

  • GeoJSON (RFC 7946) is what the MapLibre client consumes. It's also the lingua franca of contemporary web mapping; any researcher who knows the format can drop it into QGIS, Leaflet, kepler.gl, or open it in pandas with geopandas.read_file.
  • CSV is the format faculty often have in hand from their own research — a spreadsheet of places. Producing CSV with a POINT(lon lat) WKT column means the same dataset can be opened in Excel, loaded into QGIS as a delimited-text layer, or ingested by tabular tools.
  • Shapefile is still the ESRI interchange format. It's how a library exchanges geospatial data with state-level GIS offices, the Big Ten Academic Alliance Geospatial Network (BTAA-GIN), and any team built around ArcGIS Pro. Generating it from the same source keeps the formats from drifting.
  • (XML is honored through the JSON-LD context — Dublin Core's native serialization — and through the optional .prj sidecar, which is WKT text inside the Shapefile bundle. A full FGDC or ISO 19139 metadata XML would be the production deliverable; for the prototype, the GeoJSON-level metadata block stands in.)

The gazetteer authority pattern

Letters in Omeka store the place written from as a literal string in dcterms:spatial (for example "Near Vicksburg, Mississippi, United States"). They do not carry coordinates. The mapping from that string to a WGS 84 coordinate happens in the presentation layer, against a curated gazetteer file: data/gazetteer.json.

This is intentional. There are three reasons not to bake geometry into the descriptive metadata of a digital edition record:

  1. Descriptive metadata should describe. A literal string place name (especially one drawn from a controlled vocabulary like the Library of Congress Subject Headings) is the durable, citable, machine-readable thing. Coordinates are derived data — useful for visualization, but they shift as digital geography is refined, projection conventions change, and gazetteers update. Keeping them out of the curatorial record means the record stays correct as the geography around it evolves.
  2. One authority file, many consumers. The same gazetteer that feeds the map's geocoding also feeds the autocomplete in the authoring UI. Replacing the gazetteer with GeoNames, with the Library of Congress NAF, or with a project-curated Linked Open Data graph is a single-file change. Every record stays untouched.
  3. Faculty partnership. A faculty PI deciding what place name to use for a record is making a curatorial decision, not a coordinate decision. The vocabulary should match how they cite the place in their writing.

The current gazetteer ships 39 entries spanning seven Civil War theaters of operations: Iowa mustering points, Iowa home counties, the Western Theater, the Atlanta Campaign, March to the Sea, the Carolinas Campaign, and the Eastern Theater. Each entry carries a canonical name, an alias list (so the gazetteer matches both "Davenport" and "Davenport, Iowa, United States"), the WGS 84 coordinate at four-decimal precision (roughly eleven meters), a kind, a theater grouping, and an optional historical note. Coordinates are public-domain values rounded from authoritative sources (USGS, GNIS, or the National Park Service for battlefields).

Why MapLibre GL JS

The posting names three web mapping libraries as required experience: Leaflet, Mapbox GL JS, and MapLibre GL JS. This prototype uses MapLibre GL JS as the primary library. The choice reflects three considerations:

  • License posture. Mapbox GL JS went from open source to a proprietary license in 2020. MapLibre GL JS is the open-source community fork of the last permissive version, and it's where active development continues for open-license web mapping. For a public-funded library, the institutional cost story is meaningfully cleaner with MapLibre.
  • Rendering capability. MapLibre and Mapbox GL JS share a WebGL vector-tile rendering pipeline that scales well to larger datasets and lets the map style be reconfigured at runtime (the timeline scrubber and layer toggles on this map exploit that). Leaflet's DOM-based rendering is simpler but caps out earlier as datasets grow.
  • Migration path. The MapLibre and Mapbox GL JS APIs are nearly identical. Switching between them as institutional preferences shift is days of work, not a rebuild. The Leaflet version of this map would be a ground-up rewrite; the Mapbox version would be a few find-and-replace edits.

The Leaflet idiom for the same map is documented at the end of this page so the prototype demonstrates fluency across both libraries rather than just one.

Accessibility for an interactive map

Interactive maps are one of the hard cases in web accessibility. The rest of this site passes WCAG 2.2 AA cleanly because the content is documents and text. A map adds two things that no other surface in the edition has: a visual encoding that does information work (color and shape distinguish soldiers), and a direct-manipulation interaction (drag-zoom-click) that doesn't map onto assistive technology gracefully.

The approach taken here:

  • The sidebar is the keyboard-accessible primary surface. The list to the left of the map is not decorative or duplicative — it is the parallel interface for keyboard and screen-reader users. Every letter is reachable via Tab, opens a popup on Enter, and the sidebar list and the map markers stay in sync with each other (aria-current updates on selection from either side). A visitor who never uses the map directly can still browse all the content and read every popup.
  • Visual encoding is doubled. Hartwell's letters are a solid orange circle. Burroughs's are a blue circle with a paper-colored center dot — a bullseye. Color is one dimension, ring pattern is the other, so the distinction survives both color-blind viewing and monochrome printing. The legend documents the encoding in text and shows both swatches.
  • Map region has descriptive ARIA semantics. The map is wrapped in role="application" with an aria-label that names what it shows and points to the keyboard alternative in the sidebar.
  • Timeline scrubber is a real HTML range input with an explicit label, aria-describedby pointing at a live readout, and full keyboard support inherited from the platform.
  • The map's status banner is an aria-live="polite" region. When Omeka becomes unreachable or a new letter is being loaded, the status updates are announced.
  • Focus indicators on the map canvas. A three-pixel bright-gold focus ring is drawn when the canvas receives keyboard focus, so users who tab into the map have a clear indication of where focus lives.

The honest unknowns. A screen reader user can hear the sidebar; they cannot meaningfully "hear" the map's spatial layout. Mature digital-humanities map projects address this by also producing a sonification, a tactile printout, or a structured prose summary of the geographic distribution. For this prototype, the sidebar plus the popups is the access path; a production version of this edition would add one of those richer alternatives.

Live polling for new letters

The map does not consume the static GeoJSON file alone. On initial load it parses letters.geojson for an instant render, and then begins a 12-second short-poll against the Omeka REST API. New records authored through the authoring form appear within seconds of submission, with a brief flash animation around the new pin and an auto-opened popup.

This pattern was chosen over Server-Sent Events or WebSockets for the same reason the pipeline uses pure Python: simplicity matches the production deployment story. Omeka S does not natively expose SSE; Cloudflare Workers or a Node middleware would add infrastructure that this prototype doesn't need. The short-poll model degrades gracefully — if Omeka is unreachable (the local Docker stack is exposed via ngrok, which is up only when the host machine is on), the map continues to render the last good snapshot and surfaces a status banner after three consecutive failures.

Full pipeline notes for the live-update path are on the Authoring Pipeline page.

The historical raster overlay

The map currently uses OpenStreetMap raster tiles as the base layer. A planned next step is to add a georeferenced historical map overlay sourced from the Library of Congress's Civil War Maps collection (public domain) — a contemporary theater map of 1862 or 1863 that lets the visitor see the campaign through the cartography of the time.

The pipeline for that overlay, written but not yet shipped in this prototype:

  1. Download the high-resolution TIFF from the LoC.
  2. Identify four or more ground control points (GCPs) — places identifiable on both the historical map and a modern reference (the Mississippi River, a major coastal city, a state border intersection).
  3. Georeference with rasterio or gdal_translate -gcp, producing a coordinate-system-aware GeoTIFF.
  4. Generate an XYZ tile pyramid with gdal2tiles.py, output to tiles/loc-civil-war-1862/.
  5. Add the tile pyramid as a toggleable raster source in MapLibre; expose it through the existing layer-toggle UI.

This is exactly the workflow the GIS Developer/Specialist posting names with the phrase "generating and hosting raster and vector tilesets from scanned maps and primary source data." The current prototype ships the structural hook (a layer-toggle control on the map page) so the addition is a no-rebuild change. The underlying pipeline is described in code at scripts/georeference-loc-map.py (placeholder for the next iteration).

Coordinate reference system

All geometry in this prototype is in WGS 84 (EPSG:4326), also denoted OGC:CRS84 in the GeoJSON output (the longitude-latitude variant that RFC 7946 requires). The .prj sidecar in the Shapefile bundle carries the full WKT description of WGS 84 so downstream consumers don't have to guess. For a production Iowa-focused dataset, reprojecting to NAD 83 Iowa State Plane (North or South zone, EPSG:26975/26976) would be the right move for accurate distance and area calculations within the state — but the source-of-truth would remain WGS 84.

What would change in production

  • Gazetteer. Replace the curated JSON with a GeoNames lookup or an LCSH-backed authority record, with project-curated overrides for unusual or contested place names. Cache the lookups so the runtime overhead is minimal.
  • Live update. The 12-second poll is honest and resilient but rough. Production would likely use Server-Sent Events out of a Node middleware that subscribes to Omeka's resource_updated hook, with the same graceful-degradation banner pattern as a fallback.
  • Tiling. Vector tiles (via tippecanoe or MapTiler) at the dataset's natural scale, served from institutional CDN, would replace the OSM raster basemap for a higher-volume edition. Historical raster overlays would live alongside.
  • Big Ten Geospatial Network publication. The Shapefile and GeoJSON exports would be deposited in the BTAA-GIN aggregator with proper FGDC or ISO 19139 metadata, so other Big Ten libraries can discover and consume them.
  • Accessibility. Add a prose-summary view of the geographic distribution at each timeline-scrubber position, generated server-side, for screen-reader-only consumers.

Appendix: The same map in Leaflet

For completeness, here's how the same letter layer renders in Leaflet's idiom rather than MapLibre's. The pattern is similar; the API surface is smaller and the rendering is DOM-based rather than WebGL.

// Leaflet equivalent — same letters.geojson, same gazetteer-driven popups.
const map = L.map('map').setView([36.5, -87.0], 4.2);
L.tileLayer('https://tile.openstreetmap.org/{z}/{x}/{y}.png', {
  attribution: '© OpenStreetMap contributors',
}).addTo(map);

const letters = await fetch('/data/letters.geojson').then(r => r.json());
L.geoJSON(letters, {
  pointToLayer: (feat, latlng) => L.circleMarker(latlng, {
    radius: 8,
    fillColor: feat.properties.creator === 'Jonathan Hartwell' ? '#b85c38' : '#2c5e7f',
    color: '#1a1410',
    weight: 2,
    fillOpacity: 0.9,
  }),
  onEachFeature: (feat, layer) => layer.bindPopup(buildPopupHTML(feat.properties)),
}).addTo(map);

This is the version that would ship if the project's audience or hosting environment preferred Leaflet — for example, a research project that doesn't need the WebGL performance ceiling and benefits from Leaflet's smaller download footprint.
